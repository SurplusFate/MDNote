# ADR-009 嵌套列表父项点击光标归位修复

- 状态：已采纳（v1.101-caretfix）
- 关联：审查 #52 收口后暴露的点击交互缺陷；与 Sprint 3 逻辑光标模型（ADR-005）正交，不改动其代码。

## 背景 / 现象

v1.100（#52 让有序列表真正嵌套渲染）上线后，真机反馈：

> 在 IR 渲染态的嵌套有序列表里逐行点击：点「第四步」（最深的叶子项）光标落在行末；
> 点「第一/二/三步」（每个都含子列表的父项）光标却落在行首。首尾不对称，不符合直觉。

headless Chromium（playwright + /usr/bin/chromium，真实 Vditor/Lute）精确复现，逐行在自身文字的
开头/中间/末尾三处点击并测量光标在可见文字内的偏移（0=开头，len=末尾）：

| 项 | 含子列表 | 点开头 | 点中间 | 点末尾 |
|---|---|---|---|---|
| 第一步 | 是 | 0(✓) | 2(✓) | **0(✗ 应为3)** |
| 第二步 | 是 | 0(✓) | 2(✓) | **0(✗)** |
| 第三步 | 是 | 0(✓) | 2(✓) | **0(✗)** |
| 第四步 | 否(叶子) | 0(✓) | 2(✓) | 3(✓) |

即：**含块级子列表（`<ol>`/`<ul>`）的 `<li>`，点在自身文字右边界时，光标被归到块首**；叶子项正常。

## 根因

与本项目任何代码无关——是 **Chromium contenteditable 的已知怪癖**：

- `<li>` 内紧跟块级子列表时，点在文字右侧边界，浏览器把光标放置在该 `<li>` 内容块的开头，
  而非文字末尾（块级子列表紧邻，落点歧义被解析到块首）。
- 进一步验证：`document.caretRangeFromPoint(点击坐标)` 在**同一边界**也返回块首（offset 0），
  与浏览器同源怪癖——说明不能靠几何 API 直接取点。
- 因此 #52 之前有序列表不会真正嵌套，该怪癖一直被藏着；嵌套渲染出来后即暴露。
- 本项目的逻辑光标代码（`collectBlocks`/`domToLogicalCursor`/`logicalCursorToDom` 等）仅在
  `transformList`（缩进/减缩进）时运行，**纯点击进入编辑不触发**，已排除嫌疑。

## 决策

在 IR 容器挂一个**窄场景** `click` 监听，只接管「含子列表的 `<li>`」：

- 取该 `<li>` 自身可见文字节点（遍历时遇到后代 `<li>` 即停，排除子列表文字）；
- 用**点击 `clientX` 在该文字节点包围盒中的横向比例 `frac`** 反推字符偏移 `round(frac * len)`
  （中文等宽，线性映射精确；英文/数字比例字体近似，但落点误差远小于「整段跳到块首」）；
- 仅当该文字节点为**单行**（`getClientRects().length === 1`）时接管，多行标签 x→字符失真则放弃；
- 延迟 `setTimeout(0)` 到 Vditor 的 `click` 处理之后落位，确保不被覆盖；
- 框选（选区非 collapsed）直接放弃，交回 Vditor；段落/引用/叶子项/不含子列表的 `<li>` 一律不接管。

其余一切交互（缩进、undo/redo、段落缩进、框选、链接/图片点击）零回归。

## 验证

- headless e2e（修复后）：四项的开头/中间/末尾点击均精确落位（第一步/二/三末尾=3，叶子项不变），
  首尾不对称消除，无 pageerror。
- 语法检查 `node --check` 通过；缩进/减缩进 e2e（10 场景）全绿，逻辑光标链路未受影响。

## 备选方案（已否）

1. 劫持 `mousedown` 用 `caretRangeFromPoint` 预设光标 → 同源怪癖，取点本身错误，无效。
2. 监听 `mouseup` 捕获 + `stopPropagation` → 会破坏 Vditor 文本拖选与其他点击逻辑，风险大。
3. 全局对所有块用横向比例接管 → 爆炸半径过大，可能干扰 Vditor 对链接/代码块/表格的点击处理；
   收窄到「含子列表的 `<li>`」是症状精确对应的最小集合。
